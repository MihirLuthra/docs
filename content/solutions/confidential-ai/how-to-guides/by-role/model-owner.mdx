As the model owner, you make sure the weights are only ever readable by your approved workload inside a TEE. You keep the key in DSM, encrypt the model, build the confidential image, and register its measurements in CCM. The model consumer then runs it.

These tasks are in the order you do them. The [end-to-end guides](/solutions/confidential-ai/how-to-guides/end-to-end/vendor-to-customer) show where they fit in each deployment.

## Before you begin

- A Fortanix DSM account, and a Fortanix CCM account (sign in at `https://ccm.fortanix.com`).
- The **zone CA certificate** of the CCM account where the workload will run. The model consumer [downloads it](/solutions/confidential-ai/how-to-guides/by-role/model-consumer#set-up-ccm) and gives it to you.
- A Linux build machine with Docker. For Confidential Containers, Ubuntu 24.04 LTS with 16 or more cores, 128 GB RAM, 100 GB free disk, `jq` and `python3`, and HTTPS access to DSM.
- Choose the runtime. Every tab set on this page follows your choice.

## Set up DSM

You need two DSM apps in one group: one that encrypts, and one that the workload uses to get the key.

1. In DSM, create a group for the model, or use an existing one.
2. Create the app the workload authenticates as. In the group, go to **APPS** and click **ADD APP**:
   - **Interface**: REST API
   - **Authentication Method**: Trusted CA
   - **DNS Name**: the certificate domain of your workload, the one you set when you [register it in CCM](#register-and-approve-in-ccm)
   - **Upload Trusted CA Cert**: the consumer's zone CA certificate
3. Click **SAVE**. Note the app's UUID.
4. Create the app you encrypt with. Click **ADD APP** again:
   - **Interface**: REST API
   - **Authentication Method**: API Key
5. Click **SAVE**, and copy its API key. Keep it with the people who encrypt models.

## Encrypt the model

<Tabs groupId="runtime">
<Tab label="Confidential Containers">

With Confidential Containers you encrypt the whole container image. Its layers are decrypted inside the TEE with a key that DSM unwraps.

1. Create `dsm-config.json`:

   ```json
   {
     "api-endpoint": "<DSM_URL>",
     "api-key": "<DSM_API_KEY>"
   }
   ```

   - `<DSM_URL>`: your DSM endpoint, for example `https://amer.smartkey.io`.
   - `<DSM_API_KEY>`: the API key of the encryption app.

2. Build and push your application image with the model inside, then encrypt it:

   ```bash
   docker run -v <PATH>/dsm-config.json:/dsm-config.json:ro \
     -v ~/.docker/config.json:/root/.docker/config.json \
     {{coco-keyprovider.artifact}}:{{coco-keyprovider.version}} /dsm-encrypt.sh \
     --fortanix-dsm-config /dsm-config.json \
     --input-image docker://<IMAGE>:<TAG> \
     --output-image docker://<ENCRYPTED_IMAGE>:<TAG> \
     --kek-name <KEK_NAME> \
     --kek-mode shared
   ```

   - `<PATH>`: the folder with `dsm-config.json`.
   - `<IMAGE>:<TAG>`: your application image.
   - `<ENCRYPTED_IMAGE>:<TAG>`: where to push the encrypted image.
   - `<KEK_NAME>`: the name of the key-encryption key in DSM.

   Use `--kek-mode per-layer` for a key per layer. Only the encrypted image is pushed.

</Tab>
<Tab label="Enclave OS">

With Enclave OS you encrypt the model files with a PGP key in DSM, using `sq-dsm`. The workload decrypts them when it starts.

1. Install `sq-dsm`, then point it at DSM:

   ```bash
   export FORTANIX_API_ENDPOINT=<DSM_URL>
   export FORTANIX_API_KEY=<DSM_API_KEY>
   export FORTANIX_APP_UUID=<TRUSTED_CA_APP_UUID>
   ```

   - `<DSM_URL>`: your DSM endpoint, for example `https://amer.smartkey.io`.
   - `<DSM_API_KEY>`: the API key of the encryption app.
   - `<TRUSTED_CA_APP_UUID>`: the UUID of the Trusted CA app.

2. Create the key in DSM:

   ```bash
   sq-dsm key generate \
     --dsm-key "<KEY_NAME>" \
     --cipher-suite "rsa4k" \
     --userid "<OWNER_EMAIL>"
   ```

   This creates a primary key and two subkeys in DSM. Other `--cipher-suite` values: `rsa2k`, `rsa3k`, `rsa8k`, `cv25519` (the default), `nistp256`, `nistp384`, `nistp521`.

3. Export its public certificate, and encrypt the model with it:

   ```bash
   sq-dsm key extract-cert --dsm-key "<KEY_NAME>" --output model.cert.pgp
   sq-dsm encrypt --recipient-cert model.cert.pgp --compression none \
     <MODEL_FILE> -o <ENCRYPTED_MODEL_FILE>
   ```

4. Put the encrypted model in your application image, with a start-up step that decrypts it. Inside the TEE, the workload authenticates with its CCM certificate, not the API key:

   ```bash
   openssl pkcs12 -export -out identity.pfx \
     -inkey /opt/fortanix/enclave-os/default_cert/app_private.pem \
     -in /opt/fortanix/enclave-os/default_cert/app_public.pem
   export FORTANIX_PKCS12_ID=identity.pfx
   sq-dsm decrypt --dsm-key "<KEY_NAME>" <ENCRYPTED_MODEL_FILE> -o <MODEL_FILE>
   ```

   Set `FORTANIX_API_ENDPOINT` and `FORTANIX_APP_UUID` in the image too, and never `FORTANIX_API_KEY`.

## Build the confidential image and measure it

The measurement identifies your workload. CCM certifies only a workload whose measurement matches the one you register.

<Tabs groupId="runtime">
<Tab label="Confidential Containers">

The measurement covers the TEE's guest and its configuration (InitData). You read it from a pod started with the same runtime and InitData as your workload, so this step needs a node with the runtime installed.

1. Create `initdata.toml`:

   ```toml
   version = "0.1.0"
   algorithm = "sha384"
   [data]
   "aa.toml" = '''
   [token_configs.ccm_as]
   ccm_domain_names = ["<CERT_DOMAIN>"]
   '''
   "cdh.toml" = '''
   [kbc]
   name = "ccm_kbc"
   url = "<DSM_URL>"
   [kbc_configs.ccm_kbc]
   dsm_app_id = "<TRUSTED_CA_APP_UUID>"
   '''
   ```

   - `<CERT_DOMAIN>`: the certificate domain of your workload in CCM.
   - `<DSM_URL>`, `<TRUSTED_CA_APP_UUID>`: as above.

2. Encode it. The workload must use exactly this value:

   ```bash
   initdata=$(cat initdata.toml | gzip | base64 -w0)
   ```

3. Start a measurement pod with runtime class `kata-qemu-nvidia-gpu-tdx` (or `kata-qemu-tdx` without a GPU), the annotation `io.katacontainers.config.hypervisor.cc_init_data` set to `$initdata`, and the same resources as your workload.
4. In the pod, fetch the TDX evidence from `http://127.0.0.1:8006/aa/evidence` and read the measurements from the quote:

   | Value | Byte offset in the quote |
   |---|---|
   | MRTD | 184 |
   | MRCONFIGID | 232 |
   | RTMR0 | 376 |
   | RTMR1 | 424 |
   | RTMR2 | 472 |
   | RTMR3 | 520 |

<Tab label="Enclave OS">

The Fortanix TDX Converter turns your image into an Enclave OS image and reports its measurements.

1. Get the converter. Ask Fortanix support for registry credentials, and use the version from the release notes:

   ```bash
   docker login cr.download.fortanix.com -u <USERNAME> -p <PASSWORD>
   docker pull cr.download.fortanix.com/tdx-converter:<VERSION>
   docker tag cr.download.fortanix.com/tdx-converter:<VERSION> tdx-converter:<VERSION>
   ```

2. Create `converter-request.json`:

   ```json
   {
     "input_image": { "name": "<IMAGE>:<TAG>" },
     "output_image": {
       "name": "<CONVERTED_IMAGE>:<TAG>",
       "auth_config": { "username": "<REGISTRY_USER>", "password": "<REGISTRY_PASSWORD>" }
     },
     "converter_options": { "push_converted_image": true },
     "tdx_enclaves_options": {
       "cpu_count": 1,
       "mem_size": "3G",
       "enable_gpu_passthrough": true
     }
   }
   ```

   - `cpu_count`, `mem_size`: the virtual CPUs and memory of the TEE. Set them to what your model needs.
   - `enable_gpu_passthrough`: `true` to give the workload GPUs; the consumer chooses which ones at run time.

   Environment variables you set with `converter_options.env_vars` can be overridden at run time. Set the ones that must not change in the image itself.

3. Run the converter:

   ```bash
   docker run --rm --privileged \
     -v /var/run/docker.sock:/var/run/docker.sock \
     -e PRESERVE_IMAGES=input,result \
     -v "$PWD/converter-request.json:/app/req.json" \
     tdx-converter:<VERSION> --request-file /app/req.json
   ```

4. Save the measurements from the response, under `config.measurements`: `mrtd`, `rtmr0`, `rtmr1`, `rtmr2` and `rtmr3`.

</Tab>
</Tabs>

## Register and approve in CCM

<Tabs groupId="runtime">
<Tab label="Confidential Containers">

1. In CCM, go to **Applications** and click **Add Application**.
2. Select **Confidential Container - CoCo** and **Intel TDX**. Enter the name, the group, and the certificate configuration (the domain and its type). Click **Add Application**.
3. Approve the application on the **Tasks** page.
4. Open the application and click **Add Build**. Enter a unique **Build Version**, then MRTD, RTMR0 to RTMR3, and MR_CONFIG_ID (the hash of your InitData).
5. Set **Coprocessors** to **Required** for a GPU workload: CCM then checks the GPU's evidence through NVIDIA NRAS. Use **Ignored** only for workloads without a GPU.
6. Click **Add Build**, and approve the build on the **Tasks** page.

</Tab>
<Tab label="Enclave OS">

1. In CCM, open your group and go to **APPLICATIONS**. Click **+ ADD APPLICATION**, select **Intel TDX** and click **PROCEED**.
2. Create the application image from the measurements. If you converted with GPU passthrough, set **NVIDIA GPU Attestation** to **Required**.
3. Go to **CONFIGURATION** and click **+ ADD CONFIGURATION**. Select **Add new configuration**, choose the image, enter a name, and select your group. Leave **Ports** and **Configuration items** empty. Click **SAVE**.
4. Approve the build and the certificate domain on the **Tasks** page.

</Tab>
</Tabs>

Until the build and its domain are approved, CCM refuses the workload's certificate, and DSM releases no key.

## Share with the model consumer

Skip this when you also run the model yourself. Otherwise the consumer runs your application through a shared workflow between your CCM account and theirs.

1. Open your group and click **COLLABORATE**, then **+ GENERATE**, then **COPY**. Send the token to the consumer.
2. When the consumer has used it, go to **COLLABORATION GROUPS**, open the **PUBLISHER** tab, and in the row's menu click **ACCEPT**.
3. When the consumer's draft workflow arrives, go to **Workflows** > **Draft**, select it, click the placeholder assigned to your group, select your application image, and click **SAVE DRAFT**.
4. When the consumer requests approval, go to **Workflows** > **Pending**, select the workflow, click **VIEW REQUEST**, then **APPROVE**.

You approve first; the consumer cannot approve until you have. You can only change your own placeholder in the workflow.

- In CCM, your application's audit log shows a successful `REQUEST_APP_CERTIFICATE` event once the workload runs.
- In DSM, the Trusted CA app's activity log shows the key being used.
