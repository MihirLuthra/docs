A new model version is a new image, and a new image changes the workload's measurements. So it is a new build, which must be registered and approved before it runs. Otherwise CCM refuses its certificate, and DSM releases no key.

| Runtime | What changes |
|---|---|
| Confidential Containers | The pod's InitData changes with the new image, and the InitData is measured, in MRCONFIGID on Intel TDX and HOSTDATA on AMD SEV-SNP. |
| Enclave OS | The image is converted again, which gives it new measurements. |

## Build the new version

The model owner encrypts the new model and builds the new image, as in [Protect the model](../day-0-plan-and-prepare/protect-the-model.mdx), then pushes it.

## Register and approve the build

The model owner [adds a build](/products/fortanix-armor/confidential-computing/ccm/applications/register-an-application#add-a-build) with a new **Build Version**, and [approves it](/products/fortanix-armor/confidential-computing/ccm/applications/approve-builds-and-domains).

The old build stays approved, so workloads of the old version still get certificates.

## Update the shared workflow

Skip this when one organization both owns and runs the model. An approved workflow can't be edited. **EDIT WORKFLOW** creates a new version, which replaces the old one once both sides approve it.

## Redeploy

The model consumer [deploys](../day-1-deploy/deploy-and-verify.mdx) the new image. The workload attests again and gets its certificate and key as on day 1.

## Verify

- The new build is **Deployed** on the application's **Builds** tab, and the audit log shows a successful `REQUEST_APP_CERTIFICATE` after the restart.
